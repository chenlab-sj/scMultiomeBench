# multiomeBench

Code and processed results for a benchmark of single-cell RNA + ATAC integration methods,
published in *Genomics, Proteomics & Bioinformatics* (GPB).

## 1. What this is

This repository contains everything used to produce the figures and tables of the benchmark:
preprocessing, per-method integration runs, metric computation, and plotting. The benchmark asks how
well integration methods align **independently sequenced (unpaired) scRNA-seq and scATAC-seq** — the
setting in which the two modalities come from different cells, so no cell-to-cell correspondence exists
to lean on. Six datasets are used, spanning healthy PBMC (three: 10x 3k, 10x 10k, Parse Biosciences),
bone marrow mononuclear cells, breast cancer and rhabdomyosarcoma. Fourteen integration methods are
benchmarked across the datasets (thirteen have run directories in all six; Cobolt's surviving runs
cover four — its PBMC 10k values come from the published baselines and it is excluded from the BMMC
figures); the primary PBMC 3k benchmark extends to 23 method configurations, and the BMMC dataset
adds six batch-aware variants. Methods are scored on three axes: preservation of biological
diversity (cell-type structure retained after integration), reduction of the omics gap (how far the two
modalities are mixed), and cross-modality alignment (whether a cell's true identity can be recovered
across modalities, by label transfer and by chromatin-accessibility agreement).

### Datasets

| Directory | Dataset | System | Source and access |
|---|---|---|---|

| `datasets/pbmc10k` | PBMC 10k | Human PBMC | 10x Genomics public multiome — open |
| `datasets/pbmc_parse` | Parse PBMC | Human PBMC | Parse Biosciences Evercode WT Mini v3 public dataset — open |
| `datasets/bmmc_d1` | BMMC | Human bone marrow | Public multiome — open |
| `datasets/brca` | Breast cancer | HTAN WUSTL | dbGaP **phs002371.v3.p1** — **controlled access**, requires an approved dbGaP data access request. Samples: HT243B1-S1H4 (Synapse `syn53214720` RNA / `syn53215789` ATAC) and HT263B1-S1H1 (`syn53214683` / `syn53215774`), the paired multiome training sample for HT243 |
| `datasets/rms` | Rhabdomyosarcoma | Patient-derived tumour | GEO **GSE209784** — open, generated by the authors |

### Composite score

The composite score averages six metrics for unpaired data:

| Metric | Axis |
|---|---|
| `ks_celltype_mean` | biological diversity preservation |
| `asw` | biological diversity preservation |
| `omics_asw` | omics gap reduction |
| `ks_inter_celltype_mean` | omics gap reduction |
| `average_accu` | cross-modality alignment (KNN label transfer) |
| `peakdist_adj` | cross-modality alignment (pseudobulk peak agreement) |

Paired (true multiome) data adds three same-cell metrics — `ks.statistic`, `ari`, `ami` — for nine in
total. These three are defined only when the same cell is measured in both modalities, so they are
**undefined for the independently sequenced datasets**; this is why some figures show a 9-metric matrix
and others a 6-metric matrix. KNN label transfer uses k = 10, cosine distance, distance-weighted.

Inside each dataset:

```

```

## 3. Quick start

```bash
git clone <repository-url> multiomeBench
cd multiomeBench

# 1. Set your paths. config.local.sh is gitignored and is the only file you edit.
cp config/config.local.sh.example config/config.local.sh
$EDITOR config/config.local.sh          # set DATA_ROOT and PROJECT_ROOT

# 2. Create the environment for the method or stage you want to run.
conda env create -f envs/conda/<name>.yml
conda activate <name>
```

`config/config.sh` defines four variables and sources `config.local.sh` if present:

| Variable | Meaning | Placeholder default |
|---|---|---|
| `DATA_ROOT` | Raw and intermediate data (h5ad / h5 / fragments) | `/path/to/data` |
| `PROJECT_ROOT` | This checkout | the repository root |
| `BENCHMARK_FUN_DIR` | Vendored helper libraries | `$PROJECT_ROOT/common` |
| `PUBLISHED_REF` | Published baseline values | `$PROJECT_ROOT/published_reference` |

The same four values are mirrored in `config/config.yaml` for Python and `config/config.R` for R. R
scripts read them via `Sys.getenv()` with placeholder defaults, following the pattern the original
`peak_similarity.R` already used; Python scripts read `config.yaml`, overridable by environment
variables of the same name.

## 4. How the pipeline is organised

Each dataset runs the same four stages, and the directory prefix is the stage order:

```
01_preprocess  →  02_methods  →  03_metrics  →  04_figures
```

Numeric prefixes are used at two levels:

* **Directory prefixes** (`01_`–`04_`) give the stage order above. Prefixes `05_` and `06_` mark
  follow-up analyses that branch off the main chain rather than continuing it — for example
  `pbmc3k/05_geneactivity_archr` (ArchR gene-activity variant, Fig S3),
  `bmmc_d1/05_crosssite` and `bmmc_d1/06_s1d1_paired`, and `brca/05_macrophage_subsample`. Each
  carries its own `02_methods` / `03_metrics` / `04_figures` substructure.
* **File prefixes inside a stage** (`00_`, `01_`, `02_`, …) give the run order within that stage. For
  example `bmmc_d1/03_metrics` runs `00_fix_bmmc_barcodes.py` → `01_prep_latents.py` →
  `02_run_bmmc_metrics.py` → `03_knn_bmmc.py` → `04_adjust_accuracy.py` → `05_peak_similarity.R`.
  Files without a prefix (helper libraries such as `benchmark_metrics_lib.py`) are imported, not run.

A file named `<script>_sub.sh` (or `_subgpu.sh`) is the LSF submission wrapper for the script of the
same name; it is the record of how that script was invoked, including resource requests.

`pipeline/` holds numbered driver scripts that record the order in which the stages were executed
across datasets. They are documentation of the execution order first and foremost — read them before
running anything end to end.

The BMMC dataset additionally contains six batch-aware method variants — `BindSC_batch`, `MIDAS_batch`,
`scJoint_batch`, `scVI_batch`, `scglue_batch`, `scglue_multiome_batch` — which feed Fig 6A and Table S4.

## 5. Reproducing a figure without rerunning the methods

Running the integration methods is the expensive part (some runs take days on a GPU node). It is not
required to redraw the figures: every plotting script in `datasets/*/04_figures/` and
`summary/04_figures/` reads metric tables, not raw data. `results/` ships the collected copies of
those processed tables, one directory per dataset named for the figure each table set feeds — see
`results/README.md` for the index. (The plotting scripts themselves read each dataset's own
`03_metrics/` working directory; the `results/` copies exist so every figure input is in the repo.)
The published baseline tables the two splicing figures need are already present under
`published_reference/`.

**`FIGURES.md` maps each manuscript figure and supplementary panel to the script that generates it**,
together with the inputs that script needs. Start there: find your panel, run the script it names with
`config.local.sh` in place.

## 6. Environments

Each integration method has its own dependency set, and several of them conflict with each other, so
there is no single environment for the repository.

| Location | Contents |
|---|---|
| `envs/conda/<name>.yml` | Per-method conda environment, exported with `conda env export --from-history` — the packages actually requested, portable across platforms. **Use these to build an environment.** |
| `envs/conda/<name>.full.yml` | Full solved export of the same environment, with exact build strings. Use to inspect or pin the versions that were actually run. |
| `envs/conda/<name>.pip.txt` | `pip freeze` of the same environment, for packages installed outside conda. |
| `envs/R/package_versions_seurat4.txt` | R version and package versions of the `seurat4` environment used by the R pipelines (Seurat/Signac preparation, Seurat CCA and WNN, Conos, peak similarity, plotting). The `seurat4` env is additionally exported as `envs/conda/seurat4*.yml`; recreate other details from the recorded versions. Note: Conos runs inside this R environment — the `concos` env named by its LSF submitter no longer exists and was never separately exported. |
| `envs/<Method>/setup_*.sh`, `verify_*.sh` | Build and verification scripts for the five methods whose environments needed hand-pinning: MIDAS, MIRA, MaxFuse, Multigrate, scButterfly. Run `setup_*.sh` to build, `verify_*.sh` to confirm the install imports and runs. |

## 7. `published_reference/`

Some figures do not recompute every value they display. Where the manuscript compares new results
against numbers reported in a previous publication, the plotting script splices those previously
published values into the matrix instead of regenerating them. `published_reference/` holds the 33 files
(31 committed; two oversized RMS tables are gitignored, available on request — see section 8)
those splices need — 30 published baseline tables and 3 ground-truth `label.csv` files — carved out of
the original working directories so the affected figures can be rebuilt from this repository alone.

Two scripts actually perform a splice: the PBMC 3k **Fig 2B** metrics matrix
(`datasets/pbmc3k/04_figures/fig2b/plot_metrics_matrix.R`) and the BRCA **Fig S6** metrics matrix
(`datasets/brca/04_figures/plot_metrics_matrix.R`, whose `_sub.sh` driver sets `SPLICE_PUBLISHED=1`;
its original working directory was named `figS4a`, which is why the internal comments still say so).
Other scripts contain a splice branch that is never taken (their drivers set the splice flag off);
those branches are dead code retained from the original scripts and can be ignored.

Files here are inputs, not outputs of this repository. They are grouped by dataset
(`published_reference/{pbmc3k,pbmc10k,bmmc_d1,brca,rms}/`) and reached through the `PUBLISHED_REF`
configuration variable.

## 8. Known limitations

* **Three published panels have no generator in this repository: Fig S7, Fig 4C and Fig 5C.** In
  each case the published image predates every candidate script that survives in the source tree, and
  its content does not match what any shipped script draws, so it came from the original pre-revision
  working directory, which is not part of this repository. Fig S7 is the whole figure; Fig 4C is the
  three-method BRCA confusion grid with its cell-count bar; Fig 5C is the RMS MYOD1 / FOXO1 pileup
  panel (the shipped pileup script draws the 14-method Fig S8/S9 grids on a different method
  selection). These three panels cannot be regenerated from this code as it stands. `FIGURES.md`
  records the evidence for each.
* **Fig S8 and Fig S9 need two files that are not committed.**
  `predicted_ataclabel_foxo1value.csv` (88.7 MB) and `predicted_ataclabel_myod1value.csv` (18.1 MB)
  exceed what is reasonable to host in a git repository and are gitignored. They are **available from
  the authors on request**; the S8/S9 scripts will fail without them.
* **Scripts were written for an LSF cluster.** Every `*_sub.sh` / `*_subgpu.sh` driver contains
  site-specific `bsub` directives — queue names, resource strings, GPU requests, module loads — that
  will not work outside the originating cluster. Read them as a record of how each step was run and how
  much compute it needed, and translate them to your own scheduler.
* **Paths are being migrated to the `config/` convention.** The configuration mechanism described in
  section 3 is the intended way for scripts to locate data; not every script has been converted to it
  yet, and some still carry absolute paths from the original cluster. If a script cannot find its
  input, check for a hard-coded path near the top before assuming the data is missing.
* **The BRCA dataset is under controlled access.** BRCA figures cannot be reproduced from raw data
  without an approved dbGaP request for phs002371.v3.p1. Only aggregated BRCA values are carried in
  this repository (the tables under `published_reference/brca/`); no BRCA object, fragment file or
  per-cell table may be redistributed.
