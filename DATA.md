# Data availability

This repository contains **code**, **published reference values**, and **ground-truth label tables**.
It does **not** contain raw sequencing data, aligned matrices, fragment files, or intermediate
integration outputs. This document lists every input the pipeline consumes, where it comes from, and
how to obtain it.

Five of the six datasets are openly available. One (BRCA) is controlled access and requires an
approved dbGaP Data Access Request.

## 2. Where the data is expected to live

`config/config.sh`, `config/config.yaml` and `config/config.R` define `DATA_ROOT` with a placeholder
default (`/path/to/data`). Copy the example and set your own path:

```bash
cp config/config.local.sh.example config/config.local.sh
# edit DATA_ROOT and PROJECT_ROOT; config.local.sh is gitignored
```

The layout, as the preprocessing scripts actually read it (note that the BMMC and RMS arms keep the
original working-directory names, uppercase and with an `NCBI_sra` level):

```
$DATA_ROOT/
  pbmc3k/           pbmc10k/          pbmc_parse/
  BMMC/NCBI_sra/{s1d1,s2d1,s4d1}/outs/
  HTAN/{HT243B1-S1H4,HT263B1-S1H1}/   (BRCA)
  RMS/<sample>/<sample>/outs/
```

> **Status note.** Absolute cluster paths have been scrubbed from every script. Shell scripts source
> `config/config.sh` and resolve paths from it at run time; `.py` and `.R` scripts instead carry
> **literal placeholder paths** (`/path/to/data/...`, `/path/to/multiome...`) at the top of the file —
> they do not perform a live config lookup. Before running a `.py`/`.R` script, edit the placeholder
> block at its top (or set the matching environment variables where the script reads them via
> `Sys.getenv()`) to point at your `DATA_ROOT`. The placeholders preserve the original directory
> layout, so the tree above is exactly what the scripts expect under your data root.

## 3. PBMC 3k

**What it is.** 10x Genomics public Single Cell Multiome ATAC + Gene Expression demonstration data:
peripheral blood mononuclear cells from a healthy donor with granulocytes removed by cell sorting,
~3,000 nuclei. RNA and ATAC are measured in the *same* nuclei, which is what makes it usable as
ground truth for the same-cell metrics (ARI, AMI, omics KS).

**Source / access.** Open. 10x Genomics dataset portal (`https://www.10xgenomics.com/datasets`),
dataset "PBMC from a healthy donor – granulocytes removed through cell sorting (3k)", Cell Ranger ARC
1.0.0. No registration or agreement is required.

**Files consumed** (names are literal, as read by `datasets/pbmc3k/01_preprocess/data_prep.R`):

| File | Used for |
|---|---|
| `pbmc_granulocyte_sorted_3k_filtered_feature_bc_matrix.h5` | RNA + peak counts |
| `pbmc_granulocyte_sorted_3k_atac_fragments.tsv.gz` (+ `.tbi`) | fragment-level coverage for the peak-distance metric |

**Benchmark design.** `01_preprocess/0_pbmc3k_data_design.R` splits the cells 40 % train / 60 % test
(`set.seed(420)`), then splits the test half again 50/50 into an RNA-only and an ATAC-only set. The
integration methods therefore see two disjoint cell sets, but because the split is by barcode the
true pairing is still known for evaluation. The intended outputs are
`*_train.h5`, `*_test.h5`, `*_test1_rna.h5`, `*_test1_atac.h5`, `*_test2_rna.h5`, `*_test2_atac.h5`,
plus matching `filtered_feature_bc_matrix_*/` MatrixMarket directories. **As committed, the script
was cloned from the pbmc10k design**: its input path and every `sub_h5(path=...)` output name say
`10k`. To produce the `pbmc_granulocyte_sorted_3k_*_{train,test}.h5` files the `02_methods/`
scripts (e.g. Seurat_WNN) read, point `bcmtx.h5` at
`pbmc_granulocyte_sorted_3k_filtered_feature_bc_matrix.h5` and change the output names from `10k`
to `3k`; the split logic is otherwise identical.

**Approximate size.** ~2 GB, almost entirely the ATAC fragments file; the filtered matrix h5 is tens
of MB.

**Ground truth in this repo.** Cell-type labels at `results/pbmc3k/fig2b/label.csv`.

## 4. PBMC 10k

**What it is.** The same 10x Genomics multiome assay and donor protocol at ~10,000 nuclei. Used as an
independent replicate to show that the ranking is not specific to one cell count.

**Source / access.** Open. 10x Genomics dataset portal, "PBMC from a healthy donor – granulocytes
removed through cell sorting (10k)", Cell Ranger ARC 1.0.0.

**Files consumed** (`datasets/pbmc10k/01_preprocess/00_data_prep.R`):

| File | Used for |
|---|---|
| `pbmc_granulocyte_sorted_10k_filtered_feature_bc_matrix.h5` | RNA + peak counts |
| `pbmc_granulocyte_sorted_10k_atac_fragments.tsv.gz` (+ `.tbi`) | fragment coverage |

**Benchmark design.** Same 40/60 train-test split and the same second-level RNA-only / ATAC-only
split as PBMC 3k.

**Approximate size.** ~6 GB, dominated by the fragments file.

**Figures.** Fig S2 only (all 63 kept files for this dataset map to Fig S2).

## 5. Parse PBMC (cross-platform, truly unpaired)

**What it is.** Parse Biosciences Evercode WT Mini v3 human PBMC scRNA-seq (combinatorial barcoding,
multiple donors). This is an **RNA-only** dataset. It is used as the RNA modality of a genuinely
unpaired integration task: the ATAC modality is the unchanged `pbmc3k` multiome test ATAC. No cell in
the RNA set corresponds to any cell in the ATAC set, so ARI, AMI and the omics KS statistic are
undefined here and only the six unpaired metrics are computed.

**Source / access.** Open, no registration. The URL is recorded in
`datasets/pbmc_parse/01_preprocess/00_data_prep.R`:
`https://www.parsebiosciences.com/datasets/performance-of-evercode-wt-mini-v3-in-human-pbmcs/#download`

**Files consumed.** The Parse DGE output directory, read with `Seurat::ReadParseBio()`:
`DGE.mtx` / `all_genes.csv` / `cell_metadata.csv`. Only `Donor_1` is used.

**Preprocessing chain** (`datasets/pbmc_parse/01_preprocess/`):

| Script | What it does |
|---|---|
| `00_data_prep.R` | read Parse DGE, QC (`nFeature_RNA > 200`, `500 < nCount_RNA < 50000`, `percent.mt < 20`) |
| `01_azimuth_annotate_parse.R` | independent Azimuth cell-type annotation (avoids circular labelling from pbmc3k) |
| `02_compare_donor_composition.R`, `03_qc_confidence_donors.R` | donor selection and annotation-confidence QC |
| `04_build_integration_dataset.R` | builds `input_azimuth/`: Parse RNA (Azimuth labels, `"Other"` dropped) restricted to genes shared with the 10x feature list, plus the pbmc3k test ATAC copied in unchanged |

**Approximate size.** ~1 GB for the Parse DGE. The ATAC side is reused from `pbmc3k` and costs no
additional download.

**Figures.** Fig 6; Fig S12.

## 6. BMMC (multi-batch)

**What it is.** Public 10x Multiome (RNA + ATAC in the same nuclei) of bone marrow mononuclear cells,
three site–donor batches, referred to throughout the repo by the identifiers `s1d1`, `s2d1` and
`s4d1`. This dataset supplies the batch-effect arm of the benchmark: six methods are run in a
batch-aware variant and compared against their batch-naive counterparts.

**Source / access.** Open. The authors obtained raw sequencing from **NCBI SRA** and reprocessed it
with Cell Ranger ARC; the preprocessing script
(`datasets/bmmc_d1/01_preprocess/00_file_prep.R`) reads
`.../BMMC/NCBI_sra/{s1d1,s2d1,s4d1}/outs/filtered_feature_bc_matrix.h5` and
`.../outs/atac_fragments.tsv.gz`. The accession is **GEO GSE194122** (the NeurIPS 2021 Open
Problems multimodal benchmark, whose site–donor naming `s1d1` / `s2d1` / `s4d1` is used
throughout this repository), confirmed by the authors.

**Files consumed** (per batch):

| File | Used for |
|---|---|
| `outs/filtered_feature_bc_matrix.h5` | RNA + peak counts |
| `outs/atac_fragments.tsv.gz` (+ `.tbi`) | fragment coverage |

**Preprocessing note.** Because the three batches were peak-called independently,
`00_file_prep.R` reduces the three peak sets to a common set with
`GenomicRanges::reduce()` and requantifies every batch against it with `Signac::FeatureMatrix()`.
All downstream method runs therefore share one peak vocabulary.

**Approximate size.** The three fragment files total **~6.4 GB**
(recorded in `datasets/bmmc_d1/03_metrics/05_peak_sub.sh`); the matrix h5 files add a few hundred MB.

**Figures.** Fig 6A (with the `_batch` variants), Fig 6B, Fig S11, Table S4.

**Ground truth in this repo.** `results/bmmc_d1/label.csv` (48,454-cell 3-site labels) and
`results/bmmc_d1/sum_metrics_clean.csv`.

## 7. BRCA — controlled access

**What it is.** Human breast cancer tissue from the Human Tumor Atlas Network (HTAN), WUSTL
(Washington University in St. Louis) atlas. Two samples are used:

| Sample | Role | RNA object | ATAC object |
|---|---|---|---|
| **HT243B1-S1H4** | benchmark test sample | `syn53214720` → `HT243B1-S1H4.rds` | `syn53215789` → `HT243B1-S1H4.rds` |
| **HT263B1-S1H1** | paired multiome **training** sample for HT243 | `syn53214683` → `HT263B1-S1H1.rds` | `syn53215774` → `HT263B1-S1H1.rds` |

The ATAC objects carry a `peaksMACS2` assay; the ATAC fragments file
`HT243B1-S1H4-atac_fragments.tsv.gz` is also required and must be tabix-indexed
(`tabix -p bed`, as noted in `datasets/brca/01_preprocess/00_data_prep.R`).

### Access route (read this before requesting)

This dataset is **not open**. Obtaining it takes two steps and cannot be scripted.

1. **dbGaP authorization.** Study accession **`phs002371.v3.p1`** (HTAN WUSTL). Submit a Data Access
   Request through dbGaP:
   - Sign in to dbGaP with an eRA Commons (or equivalent) account at
     `https://dbgap.ncbi.nlm.nih.gov/`.
   - Open the study page for `phs002371` and start a DAR. You will need a signing official at your
     institution to countersign, a research use statement, and agreement to the study's Data Use
     Certification. Approval is granted per project, is time limited, and requires renewal.
   - Turnaround is typically weeks, not days. Budget for it.
2. **Retrieval from Synapse.** Once the DAR is approved, the processed Seurat objects are downloaded
   from Synapse (`https://www.synapse.org/`) using the Synapse IDs in the table above. Create a
   Synapse account, link it to your approved dbGaP credentials, and download either through the web
   client or `synapseclient`:

   ```bash
   pip install synapseclient
   synapse get syn53214720 syn53215789          # HT243B1-S1H4 RNA / ATAC
   synapse get syn53214683 syn53215774          # HT263B1-S1H1 RNA / ATAC (training)
   ```

   Place the results so that the layout matches what `00_data_prep.R` expects:
   `$DATA_ROOT/HTAN/HT243B1-S1H4/<synapse_id>/<sample>.rds` (and
   `$DATA_ROOT/HTAN/HT263B1-S1H1/<synapse_id>/<sample>.rds` for the training sample) — note the
   `HTAN/` directory name, kept from the original working layout. Run
   `00_download/download_brca.sh` to verify the layout once everything is in place.

**Redistribution.** Do not commit any BRCA object, fragment file, barcode list, or per-cell table to
a public repository. The tables that *are* in this repo
(under `results/brca/`) are aggregated metric values and de-identified cell-type labels only.

**Approximate size.** ~5 GB for the four `.rds` objects plus the fragments file.

**Figures.** Fig 4A–D, Fig S4, Fig S5, Fig S6.

## 8. RMS (rhabdomyosarcoma)

**What it is.** 10x Single Cell Multiome ATAC + Gene Expression on rhabdomyosarcoma tumours,
generated by the authors. The benchmark test sample is **Mast607A** (`Mast607A_TB19_22652`); two
further samples serve as the paired training/reference set:

| Sample | Role |
|---|---|
| `Mast607A_TB19_22652` | test sample (all RMS figures) |
| `Mast39_TB12_1442` | training / reference sample; also the source of the reference `features.tsv` |
| `MAST213F_TB15_5705` | second training / reference sample |

**Source / access.** Open. **GEO accession `GSE209784`**, generated by the authors of this benchmark.

**Processing.** FASTQs are processed with `cellranger-arc count` (v2.0.0) against a **GRCh37/hg19**
reference — see `datasets/rms/01_preprocess/00_cellranger_arc_sub.sh`. Note the genome build: the RMS
arm is hg19, unlike the hg38 PBMC/BMMC/BRCA arms, so peak coordinates are not interchangeable across
datasets. `01_make_common_peak_h5.R` then reduces the three samples' peak sets to a common set and
rewrites per-sample h5 files against it.

**Files consumed** (per sample): `outs/filtered_feature_bc_matrix.h5`,
`outs/filtered_feature_bc_matrix/features.tsv`, `outs/atac_fragments.tsv.gz` (+ `.tbi`).

**Approximate size.** Tens of GB for the Cell Ranger outputs of the three samples.

**Figures.** Fig 5A, Fig 5B, Fig 7, Fig S7, Fig S8, Fig S9, Fig S10, Fig S13, and the RMS panel of
Fig S1.

**Fig S7 additional sample.** The Fig S7 Multiome-vs-Annotation pileup strips
(`datasets/rms/04_figures/figS7_multiome_vs_annotation/`) are drawn on the RMS scATAC sample
**SJRHB013758_X2**, with the Multiome row taken from the paired Mast607A data. SJRHB013758_X2 is
not part of GSE209784; it is a public scATAC-seq sample from the St. Jude pediatric
rhabdomyosarcoma atlas, GEO **GSE174376** (sample **GSM5390512**, `SJRHB013758_X2_scATAC`, an
orthotopic patient-derived xenograft; Patel et al., *Dev Cell* 2022, PMID 35483358). The scripts
read the GEO supplementary fragments file under its original name
(`GSM5390512_1951549_DYE3118_fragments.tsv.gz`). The per-cell `predicted_ataclabel_*value.csv`
tables those scripts read are not committed (size); they are available from the authors on request,
like the Fig S8/S9 inputs. Fig 5C uses the same pileup code as Figs S8/S9 with a different method
selection — see FIGURES.md.

**Ground truth in this repo.** `results/rms/label.csv`, `results/rms/sum_metrics_clean.csv` and
the `results/rms/knn_test/` prediction tables.

## 9. What is not in this repository, and why

| Not included | Size | Why | How to get it |
|---|---|---|---|
| Raw FASTQ, Cell Ranger `outs/`, fragment files, `.h5`, `.h5ad`, `.rds`, `.RData`, BAM, bigWig | **~250 GB total; largest single file 21.6 GB** | GitHub rejects files over 100 MB and this volume is not distributable through git at all | Sections 3–8 above; `00_download/` for the open datasets |
| Per-method intermediate outputs (latent embeddings for every method × dataset × replicate, ArrowFiles, model checkpoints) | tens of GB | regenerable by rerunning `02_methods/`; not primary data | rerun the method scripts, or contact the authors |
| `results/` — merged final tables, per-metric tables, per-method latents, reference tables and ground-truth labels (see `results/README.md`) | small (a few hundred MB) | kept out of version control by policy | **available directly from the authors on request** |

The file-type exclusions are enforced by `.gitignore` (`*.h5`, `*.h5ad`, `*.rds`, `*.RData`, `*.mtx*`,
`*.tsv.gz`, `*.bam`, `*.bw`, `*.npy`, `ArrowFiles/`, `results/`, …), which also blocks
`config/config.local.sh` so that no local path map is ever published.

**What *is* included**: every script under `datasets/`, `summary/`, `pipeline/` and `config/`. The
figure input tables under `results/` are not published in this repository — contact the authors for
a copy.

## 10. `00_download/` — fetch scripts for the open datasets

`00_download/` holds one fetch script per openly available dataset. These scripts are authored
separately from this document; the contract they follow is:

- **One script per dataset**, named for the dataset key: `download_pbmc3k.sh`, `download_pbmc10k.sh`,
  `download_pbmc_parse.sh`, `download_bmmc_d1.sh`, `download_rms.sh`.
- Each script sources `config/config.sh`, so it honours `DATA_ROOT` from `config.local.sh` or from the
  environment.
- Each script downloads **only its own dataset**, into `$DATA_ROOT/<dataset>/`, using the exact
  filenames the preprocessing scripts in `datasets/<dataset>/01_preprocess/` expect. Nothing is
  renamed after download.
- Downloads are idempotent: a file already present with the right size is not refetched, so an
  interrupted run can simply be rerun.
- Checksums, where the provider publishes them, are verified after download.
- Nothing is unpacked into the repository tree — the repository and `DATA_ROOT` stay disjoint.

**BRCA cannot be fetched by script**: the dbGaP + Synapse route in section 7 requires an
authenticated, individually approved account and cannot be automated in a public script.
`download_brca.sh` therefore only verifies that the expected `$DATA_ROOT/HTAN/` layout is in place
and prints the access route — it downloads nothing.

Downloads only fetch; they do not preprocess. After downloading, run the dataset's
`01_preprocess/` scripts in numeric order to produce the integration inputs.
